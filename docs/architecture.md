# Архитектура

## Компоненты

| Компонент | Что делает |
| --- | --- |
| `app/news` | сбор новостей из источников, нормализация, дедупликация, хранение в ленте |
| `app/profile` | профиль компании по выгрузкам кейса: отрасль, размер, продукты банка, регионы, контрагенты, группа |
| `app/rank` | отбор кандидатов из ленты под профиль и ранжирование по значимости |
| `app/agent` | оркестратор: план, вызов инструментов, общий контекст, самопроверка, сборка ответа |
| `app/api` | HTTP-контракт для фронтенда, схемы ответов, OpenAPI |
| `app/worker` | фоновые задачи: периодический сбор, пересчёт витрин, прогрев сводок |
| `app/llm` | HTTP-клиент LLM, выбор модели, повторы и общий бюджет через Redis |
| `frontend` | интерфейс: лента событий, карточка вывода, панель источников |

Хранилище — PostgreSQL: новости, профили, связи и готовые выводы. Очередь фоновых задач — Redis через arq.

## Поток данных

```
источники новостей ──┐
                     ├─► нормализация ─► лента событий ─┐
аналитика банка ─────┘                                  │
                                                        ├─► отбор кандидатов ─► ранжирование ─► агент ─► вывод
выгрузки кейса ─► витрина клиента ─► профиль компании ──┘                                        │
                                                                                    источники ◄──┘
```

Вывод хранится вместе со ссылками на всё, что в него попало: идентификаторы новостей, поля профиля, фрагменты аналитики банка. Панель источников в интерфейсе читает именно эти ссылки, а не пересобирает их заново.

## Отбор без эмбеддингов

Отбор кандидатов строим на лексическом поиске: BM25 по тексту новости и расширенному запросу, собранному из профиля компании (ОКВЭД и его словесные формулировки, регионы, названия продуктов банка, отраслевые термины). Переранжирование верхних кандидатов делает LLM из разрешённого списка.

Причина — в [decisions/0002-otbor-bez-embeddingov.md](decisions/0002-otbor-bez-embeddingov.md): кейс ограничивает список моделей, и эмбеддинг-модели в нём не названы.

## Агентный цикл

Кейс требует агентной логики и запрещает брать готовые мультиагентные фреймворки как основной компонент. Поэтому цикл пишем сами:

1. **План.** По профилю компании и набору кандидатов агент формирует список шагов: что проверить, какие инструменты вызвать.
2. **Инструменты.** Каждый инструмент — обычная функция с описанной схемой входа и выхода: поиск по ленте, чтение профиля, выборка контрагентов, поиск по аналитике банка, расчёт по платежам.
3. **Общий контекст.** Шаги пишут результаты в один объект контекста, который переживает весь разбор события и доступен следующим шагам.
4. **Самопроверка.** Перед сборкой ответа агент проверяет утверждения на наличие источника и на противоречия, и помечает то, что не подтверждается.
5. **Адаптация.** Если проверка не прошла или данных не хватило, агент меняет план: уточняет запрос, берёт другой инструмент или честно отвечает, что значимой связи нет.

Каждый шаг пишет структурный лог с идентификатором разбора: модель, инструмент, длительность, стоимость. По этому логу собирается трассировка в интерфейсе и считается расход бюджета.

## Границы

- Весь доступ к LLM идёт через `app/llm`: лимиты, ретраи, учёт стоимости и выбор модели живут там. Настройки остаются в `app/core/config.py`.
- Данные кейса читаются только через витрину профиля: модули отбора и агента не знают про формат CSV.
- Фронтенд не ходит в LLM и не содержит бизнес-логики отбора — только показывает то, что отдал API.
