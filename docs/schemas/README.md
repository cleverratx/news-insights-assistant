# Контракты обмена между компонентами

Семь JSON-схем, по которым модули передают данные друг другу и фронтенду. Кейс прямо рекомендует структурированный обмен: факты, источники, признаки клиента, оценки релевантности, риски и возможности — с разделением подтверждённой информации, аналитики банка и выводов модели.

| Схема | Кто пишет | Кто читает | Что это |
| --- | --- | --- | --- |
| [company_profile](company_profile.schema.json) | `app/profile` | `rank`, `agent`, фронтенд | бизнес-контекст компании и список признаков, на которые можно сослаться |
| [news_item](news_item.schema.json) | `app/news` | `rank`, `agent`, фронтенд | новость или материал аналитики банка после нормализации и классификации |
| [ranked_item](ranked_item.schema.json) | `app/rank` | `agent`, фронтенд | материал, отобранный под компанию, с разложением оценки и совпавшими признаками |
| [insight](insight.schema.json) | `app/agent` | фронтенд, API | ответ на шесть вопросов кейса со ссылками на источники |
| [knowledge_base](knowledge_base.schema.json) | `app/profile/knowledge.py` | `agent`, `rank`, фронтенд | факты о компании от системы, данных банка и клиента; факт клиента главнее |
| [knowledge_gaps](knowledge_gaps.schema.json) | `app/profile/gaps.py` | фронтенд, агент | вопросы клиенту о том, чего система не знает, и предположения на подтверждение |
| [linked_companies](linked_companies.schema.json) | `app/profile/links.py` | фронтенд, агент | карточки связанных компаний: оборот и доля по платежам, группа, тип связи от клиента |

## Источник правды — код

Схемы генерируются из Pydantic-моделей в `backend/app/contracts` и руками не правятся. После изменения моделей:

```
cd backend
uv run python -m app.contracts
```

Тест `tests/test_contracts.py` падает, если файлы в этой папке отстали от кода, и проверяет, что примеры из [examples/](examples/) проходят валидацию. Примеры синтетические: компания, новость и тексты аналитики придуманы для иллюстрации формата.

Каждый документ несёт `schema_version`. Несовместимое изменение — новая версия, а не тихая правка.

## Как устроена прослеживаемость

```
CompanyProfile.features[].id ──────┐
NewsItem.id + fragments/key_facts ─┼─► Insight.sources[] ◄── statement.source_ids
                                   │        (SourceRef)
RankedItem.matched_features ───────┘
```

- Каждое утверждение вывода (`Statement`) ссылается хотя бы на один `SourceRef` из `Insight.sources`. Источник бывает трёх типов: `news`, `bank_analytics`, `profile_feature`.
- У утверждения есть `origin` — откуда оно взялось. Это то, что видит пользователь: где позиция банка, а где вывод AI.

| `origin` | Значит | Обязан ссылаться на |
| --- | --- | --- |
| `fact` | подтверждено материалом | новость или аналитику банка |
| `bank` | позиция Альфа-Банка | аналитику банка |
| `client_data` | следует из данных о компании | признак профиля |
| `model` | вывод модели | любой источник |

## Шесть вопросов кейса → поля `Insight`

| Вопрос | Поле | Правило, которое проверяет модель |
| --- | --- | --- |
| Что произошло | `what_happened` | только `fact` или `model`; статус факта в новости — `KeyFact.status` |
| Почему важно этой компании | `why_it_matters` | каждое утверждение ссылается на признак компании — иначе это не персонализация |
| Какие последствия | `risks`, `opportunities` | готовый вывод называет хотя бы один риск или возможность |
| Какие действия | `actions` | `kind`: действие, вопрос, сценарий или продукт банка; продукт — только при `bank_product` |
| Как оценивает банк | `bank_view` | только `origin=bank` со ссылкой на аналитику банка |
| На чём основан вывод | `sources` | все `source_ids` существуют, все `news_ids` есть среди источников |

«Значимой связи нет» — допустимый ответ: `status=no_significant_link` или `insufficient_data` с обязательной причиной в `status_reason`. Так агент не обязан выдумывать связь, если её нет.

`self_check` хранит результат самопроверки агента: сколько было итераций и какие замечания нашлись и исправлены. `run_id` связывает вывод с журналом шагов агента для трассировки.
