# Данные кейса

Организаторы дают обезличенный набор данных о юридических лицах — клиентах корпоративного бизнеса банка — и связанных с ними физических лицах. Идентификаторы работают только внутри набора и не позволяют определить реальные организации или людей.

## Правила обращения

- Выгрузки не коммитятся. Локально они лежат в `data/raw/`, этот путь закрыт `.gitignore`.
- В `data/samples/` кладём только синтетические строки, собранные вручную, — для тестов и демо.
- Производные витрины (parquet, csv, дампы) тоже не коммитим: они собираются скриптами из `data/raw`.
- В логи и в ответы сервиса не выносим сырые идентификаторы: наружу идёт то, что нужно для вывода.

## Профиль данных и эталонные компании

Два скрипта собирают всё, что нужно знать о выгрузках, и переизбираются в один проход. Руками отчёты не правим — они пересобираются из данных.

```
cd backend
uv run python scripts/profile_data.py ../data/raw/df_Uid_data_hack.csv ../data/raw/df_Fid_Uid_link_hack.csv --out ../docs/data-profile.md
uv run python scripts/pick_demo_companies.py ../data/raw/df_Uid_data_hack.csv ../data/raw/df_Fid_Uid_link_hack.csv -n 3 --out ../docs/demo-companies.md --legend ../data/samples/legends.generated.yaml
```

`profile_data.py` (задача A1-08) проверяет файлы на соответствие приложению 1 кейса, считает заполненность и уникальность каждого поля, распределение выручки, топы отраслей и регионов, долю компаний с каждым продуктом банка и с признаком ФТС, покрытие платежами и число контрагентов на компанию, а в конце отмечает поля-константы и поля с пропусками больше половины строк — их нельзя брать в признаки не глядя.

`pick_demo_companies.py` (задачи A1-09 и A2-11) отбирает эталонные компании для демо. Обязательные условия: ВЭД (`FTS_FLAG`), кредит или лизинг, группа компаний (`GROUP_ID`, в группе больше одного юрлица) и от 5 контрагентов в платежах без платежей самому себе — на бедной строке половина признаков профиля не отработает. Из прошедших берётся по одной компании на роль: импортёр (ОКВЭД 45–46), производство (10–33), услуги или ритейл (47, транспорт, IT, недвижимость и прочие услуги), внутри роли — по баллу за продукты, контрагентов, связанных физлиц, заполненность полей и выручку уровня крупного бизнеса. Если подходящей компании на роль нет, слот добирается подходящей компанией другой отрасли, а если подходящих не осталось — лучшей из остальных, и в карточке перечислено, чего ей не хватает. На выходе — карточки с признаками, крупнейшими контрагентами и темами, которые должны отзываться в ленте, плюс заготовка легенды для демо, правила для неё — в [ADR 0003](decisions/0003-demo-legenda.md).

Платежи в реальной выгрузке лежат в отдельном файле `df_Uid_payment_hack.csv`, хотя в описании кейса они отнесены к `df_Fid_Uid_link_hack.csv`. Оба скрипта ищут его рядом с файлом связей сами, путь можно задать через `--payments`. Платежи самому себе (получатель равен плательщику) отбрасываются. Отбор демо-компаний по умолчанию ограничен целевым сегментом кейса — выручкой от 15 млрд, порог задаётся через `--min-revenue`.

Скрипты ничего не скачивают и не ходят в сеть: на вход — только локальные файлы выгрузки.

## Загрузка в PostgreSQL

Задача A2-01. Модуль `app/data` читает обе выгрузки, чистит значения и одной транзакцией перезаливает таблицы `companies`, `persons` и `payments`. Повторный запуск безопасен: таблицы заменяются целиком, а при ошибке остаются прежними.

```
# в Docker: выгрузки лежат в data/raw, каталог data смонтирован в контейнер
docker compose run --rm api python -m app.data

# локально
cd backend
uv run python -m app.data --companies ../data/raw/df_Uid_data_hack.csv --links ../data/raw/df_Fid_Uid_link_hack.csv
```

`--dry-run` разбирает файлы и печатает отчёт без записи в базу. `--samples` берёт синтетические выгрузки из `data/samples` — с ними сквозной сценарий проходится без настоящих данных, состав описан в [data/samples/README.md](../data/samples/README.md). `--payments` принимает отдельный файл платежей: в выданном файле связей столбцов `PAYER`, `BENEFICIARY`, `PAY_AMT`, `PAY_CNT` нет, хотя кейс их описывает. Если они появятся в файле связей, загрузчик возьмёт их оттуда сам.

Что делает с данными:

| Проблема | Что делаем |
| --- | --- |
| кодировка и разделитель | UTF-8 с BOM или cp1251; разделитель (точка с запятой, запятая, табуляция или вертикальная черта) определяется по заголовку |
| пустые значения | `nan`, `null`, `—`, `н/д`, пробелы и пустые строки → `NULL` |
| флаги `*_MARK`, `FTS_FLAG`, `NEGATIVEMARK` | `1`, `1.0`, `да`, `true` → да; `0`, `нет`, `false` → нет; прочее → `NULL` и запись в отчёт |
| выручка и суммы | пробелы и разряды, запятая или точка как десятичный разделитель, `руб.` → `numeric(20,2)`; отрицательные → `NULL` |
| ОКВЭД | `46,38` → `46.38`, потерянный ноль `1.1` → `01.1`; нераспознанный код → `NULL` |
| `CL_TYPE` | только `CLIENT`, `CLOSE_CLIENT`, `PROSPECT` |
| `FTS_COUNTRY_NAME` | строка «КИТАЙ, ТУРЦИЯ» → массив стран без повторов |
| дубликаты `SYNTHETIC_U` | остаётся строка, где заполнено больше полей |
| строка без идентификатора или с лишними полями | отбрасывается: со сдвинутыми столбцами значения попадут не в свои поля |
| повторные платежи между одной парой компаний | суммируются в одну запись |

Каждый запуск пишет отчёт в таблицу `data_loads` и печатает его: сколько строк прочитано, загружено, отброшено и склеено; какие проблемы найдены, в каком поле, сколько раз и в каких строках файла. Идентификаторов и значений в отчёте нет: только номера строк.

Колонки таблиц названы по-английски, соответствие полям выгрузки — в `COMPANY_FIELDS`, `PERSON_FIELDS` и `PAYMENT_FIELDS` в `app/data/loader.py`. По этой карте профиль показывает, из какого поля взят признак. Физлица и платежи не связаны с `companies` внешним ключом: в выгрузке есть связи с компаниями, которых нет в файле юрлиц, и терять их нельзя.

## Справочник ОКВЭД

Задача A2-02, модуль `app/profile/okved.py`. Отрасль — главный признак для отбора новостей, поэтому код `MAINOKVED_CODE` раскладываем на четыре уровня:

| Уровень | Пример для `46.38` | Зачем |
| --- | --- | --- |
| раздел ОКВЭД (A–U) | G — торговля | грубая группировка по классификатору |
| класс (две цифры) | 46 — оптовая торговля | короткое название для интерфейса и запасной вариант названия |
| сегмент рынка | `food` — продукты питания и напитки | наша группировка: какие новости отзываются у компании |
| роль в цепочке | `wholesale` — опт | одна новость по-разному бьёт по производителю, оптовику и рознице |

Сегмент выбирается по самому длинному совпавшему префиксу: `46.38` попадает в «продукты питания», а не в «торговлю широкого профиля», потому что оптовик продуктами живёт новостями продуктового рынка. У каждого сегмента есть отраслевые термины для расширения поискового запроса (`keywords`) и темы новостей, к которым он чувствителен (`topics`, из того же списка, что и классификация новостей).

Неизвестные и битые коды:

- `46,38`, `1.1`, `62.01.` нормализуются в `46.38`, `01.1`, `62.01`;
- если код пустой, битый или такого класса нет (например, `34.10`), отрасль угадывается по `MAINOKVED_NAME`, а в `resolved_by` ставится `name`;
- если не помогло и название, сегмент — `other`, `resolved_by=unknown`. Профиль от этого не ломается, просто отрасль не участвует в отборе.

Новая отрасль добавляется строкой в `SEGMENTS` и `SEGMENT_BY_CLASS` или уточнением в `SEGMENT_BY_PREFIX`. Тесты проверяют, что у каждого класса ОКВЭД есть раздел и сегмент, а у каждого сегмента — термины и темы.

## Базовые признаки компании

Задача A2-03, модуль `app/profile/features.py`. На вход — строка таблицы `companies` (`CompanyRow`), на выход — признаки для профиля. У каждого признака есть идентификатор, на который ссылается вывод агента, и поле выгрузки, из которого признак получен.

| Признак | Поле выгрузки | Как считаем |
| --- | --- | --- |
| `feature:revenue` | `REVENUE_COMPANY` | «Выручка 18,2 млрд ₽ в год» |
| `feature:size` | `REVENUE_COMPANY` | вычисленный: до 120 млн — микро, до 800 млн — малый, до 2 млрд — средний (пороги МСП), от 15 млрд — крупнейший (порог кейса), между ними — крупный |
| `feature:employees` | `AMOUNT_WORKERS_FNS_GRADATION`, если пусто — `AMOUNT_WORKERS_SPARK_GRADATION` | источник указан в формулировке |
| `feature:age` | `COMPANY_AGE_YEARS_GRADATION` | «Возраст компании: 8–15 лет» |
| `feature:stage` | `ECO_MARK_LABEL` | стадия развития как есть |
| `feature:ownership` | `OKFS_NAME` | форма собственности |
| `feature:foreign_capital` | `OKFS_NAME` | вычисленный: в форме собственности есть иностранное участие |
| `feature:state_capital` | `OKFS_NAME` | вычисленный: есть государственное, региональное или муниципальное участие |
| `feature:region`, `feature:city` | `REGION`, `CITY` | у города убирается «г.» |
| `feature:client_type` | `CL_TYPE` | действующий, бывший (`CLOSE_CLIENT` — наша трактовка) или потенциальный клиент |

Чего нет в строке, того нет и в признаках: пустое поле попадает в `missing_fields`, а не превращается в догадку. Нулевая выручка не делает компанию «микро» — размер считается неизвестным. Противоречия попадают в `warnings`: численность по ФНС и СПАРК расходится, выручка от 15 млрд при штате меньше 15 человек.

## Продуктовый профиль и ВЭД

Задача A2-04, модуль `app/profile/products.py`. Из флагов продуктов и данных ФТС строим признаки и **чувствительность к темам новостей** (`exposures` в `CompanyProfile`). Это прямой мост между новостью и бизнесом: отбор и агент видят не только «у компании есть кредит», но и «ставка для неё — риск, вот почему и вот признаки».

| Признак | Поле выгрузки |
| --- | --- |
| `feature:loan`, `feature:leasing`, `feature:guarantee`, `feature:factoring`, `feature:deposit`, `feature:settlement`, `feature:payroll` | `CL_PRODUCT_*_MARK`, `FACTORING_MARK` |
| `feature:customs` — ведёт ВЭД, со списком стран | `FTS_FLAG`, `FTS_COUNTRY_NAME` |
| `feature:unfriendly_trade` — страны из перечня недружественных (распоряжение № 430-р) | `FTS_COUNTRY_NAME`, вычисленный |
| `feature:payment_hub_trade` — Китай, Гонконг, Турция, ОАЭ, Казахстан, Киргизия, Армения: там задерживают платежи из-за вторичных санкций | `FTS_COUNTRY_NAME`, вычисленный |

| Тема | Когда | Направление |
| --- | --- | --- |
| `key_rate` | кредиты, лизинг, гарантии, факторинг; депозиты | долг — риск, только депозит — возможность, и то и другое — смешанное |
| `labor` | зарплатный проект | риск: зарплаты, НДФЛ, дефицит кадров |
| `fx` | есть ВЭД | смешанное: направление (импорт или экспорт) по ФТС неизвестно; в ключевых словах — валюты стран-партнёров («курс юаня») |
| `trade` | есть ВЭД | смешанное: пошлины, таможня, параллельный импорт, страны-партнёры |
| `sanctions` | ВЭД с недружественными странами или через страны с риском платежей | риск |

Флаги продуктов — про продукты в Альфа-Банке. Отсутствие кредита у нас не значит, что у компании нет долга в другом банке, поэтому «нет продукта» не становится признаком. Для потенциального клиента без продуктов это проговаривается в `warnings`. Пустой флаг попадает в `missing_fields`, а не считается за «нет». Если страны ФТС указаны при `FTS_FLAG = 0`, ВЭД считаем подтверждённой и предупреждаем о противоречии.

## Граф связей

Задача A2-05, модуль `app/profile/graph.py`. `fetch_links` достаёт связи компании из таблиц загрузчика, `link_profile` превращает их в часть профиля.

| Связь | Откуда | Что попадает в профиль |
| --- | --- | --- |
| группа | `companies.group_id` | `group`: размер, сегменты рынка компаний группы, 10 крупнейших по выручке; признаки `feature:group` и `feature:group_segments` |
| контрагенты | `payments` | `counterparties`: по 10 крупнейших покупателей (входящие платежи) и поставщиков (исходящие) с долей оборота и сегментом; признаки `feature:counterparties_incoming` и `feature:counterparties_outgoing` |
| физлица | `persons` | число связанных лиц и их регионы (`RC_NAME`), признак `feature:persons` |
| общие физлица | `persons` × `persons` | `related_companies`: компании, с которыми клиента связывает одно и то же лицо; признак `feature:person_links` |

Ради отраслей окружения всё и делается: новость про рынок крупного покупателя важнее общеотраслевой. Поэтому сегменты превращаются в чувствительность к отраслевым новостям (`exposures` с темой `industry`):

- отрасль покупателей или поставщиков с долей от 10% оборота: «Ваши покупатели из отрасли „Гостиницы, общепит и туризм“ дают 35% оборота: спад на их рынке ударит по вашей выручке»;
- до трёх отраслей группы, отличных от отрасли самого клиента.

В ключевых словах — термины сегмента из справочника ОКВЭД, так что отбор найдёт новости рынка контрагента без отдельной настройки.

Группа из одной компании группой не считается. Контрагент, которого нет в выгрузке юрлиц, остаётся в списке без отрасли. Платежей в выданном файле нет, поэтому сейчас блок контрагентов пустой, и это проговаривается в `warnings`. Код готов: если платежи появятся, загрузчик и граф подхватят их без изменений.

## Производные признаки

Задача A2-06, модуль `app/profile/derived.py`. Это оценки поверх базовых признаков, продуктов и графа связей. Все они помечены как вычисленные, а формулировки осторожные: «вероятно импортёр», а не «импортёр».

| Признак | Как оцениваем | Что даёт выводу |
| --- | --- | --- |
| `feature:debt_dependence` | два и больше долговых продукта в банке или от 10% исходящих платежей финансовым компаниям — высокая; один продукт или меньшая доля — заметная | ставка как риск с объяснением, откуда видна зависимость |
| `feature:finance_payments` | доля исходящих платежей контрагентам из сегмента «финансы» | видно долг и лизинг в **других банках**, которых флаги продуктов не показывают |
| `feature:trade_direction` | ВЭД + место в цепочке: торговля — вероятно импорт, добыча — экспорт, производство — и то и другое; по услугам не оцениваем | валютный риск получает знак: импортёру слабый рубль вредит, экспортёру помогает |
| `feature:customer_concentration`, `feature:supplier_concentration` | доля крупнейшего покупателя или поставщика: от 50% — высокая, от 25% — средняя | от средней и выше — тема `company`: новости о контрагенте бьют напрямую |
| `feature:geography` | регион регистрации, регионы контрагентов и компаний группы, регионы связанных лиц | тема `regional` с регионами в ключевых словах |

`merge_exposures` собирает чувствительность из всех блоков профиля. По одной теме остаётся последняя оценка: уточнённая из производных признаков («вероятно импортёр, слабый рубль — риск») заменяет грубую из продуктов («смешанное»). Отраслевые темы не заменяются: у каждой отрасли окружения своя. Порядок сборки: продукты, граф, производные.

## API профиля

Задача A2-07. `GET /api/companies/{company_id}/profile` отдаёт `CompanyProfile` (схема — [schemas/company_profile.schema.json](schemas/company_profile.schema.json)). Сборка — `app/profile/builder.py`: отрасль, базовые признаки, продукты, граф связей, производные признаки и положение в отрасли. Этот же `load_profile` будет вызывать агент как инструмент.

Трассируемость начинается здесь: у каждого признака в `features` есть `source_fields` — поля выгрузки, из которых он получен, и `derived` — взят как есть или вычислен. Вся чувствительность к темам (`exposures`) ссылается на признаки, а чего в данных не хватило, перечислено в `data_quality`.

Положение в отрасли (`market_position`, `feature:market_rank`) — место по выручке среди компаний с тем же кодом ОКВЭД в загруженной выгрузке. Если таких компаний меньше 10, сравниваем с классом ОКВЭД (первые две цифры). Это оценка по базе банка, а не доля рынка страны, и формулировка признака это проговаривает.

| Код | Когда |
| --- | --- |
| 200 | профиль собран; даже у пустой строки — с пустыми признаками и списком пробелов |
| 404 | компании нет в загруженной выгрузке |
| 503 | база недоступна или выгрузка не загружена (`python -m app.data`) |

Надёжность профиля проверяет `tests/test_profile.py` (задача A2-09). Кроме отдельных случаев — все поля пустые, неизвестный ОКВЭД, нулевая выручка, пустой граф, контрагенты вне выгрузки, — он собирает профиль на 400 случайных сочетаниях битых строк и связей и на каждой строке синтетики. Для каждого профиля проверяется, что он не утверждает лишнего (критерий 04):

- у каждого признака есть поля-источники, и это поля выгрузки;
- признак, взятый «как есть», не ссылается на пустое поле;
- признак продукта есть тогда и только тогда, когда флаг равен 1;
- выручка в признаке совпадает со строкой, без выручки нет ни размера, ни признака «крупный бизнес»;
- в `missing_fields` только поля, которые пустые или не распознаны;
- доли контрагентов по направлению в сумме не больше 100%, по каждой теме одна оценка.

## База знаний компании

Задача A2-12, модель — `app/contracts/knowledge.py` (схема [schemas/knowledge_base.schema.json](schemas/knowledge_base.schema.json)), хранение и правила — `app/profile/knowledge.py`. Это то, чего нет в выгрузке, но что важно для выводов: рынки, продукция, сезонность, ограничения, поставщики, покупатели, планы.

| Поле факта | Что значит |
| --- | --- |
| `category` | `markets`, `products`, `seasonality`, `constraints`, `suppliers`, `customers`, `plans`, `other` |
| `source` | `client` — ввёл клиент, `bank_data` — из данных банка, `system` — вывела система, `legend` — из демо-легенды; при споре по одному ключу побеждает источник левее |
| `status` | `assumption` — ждёт подтверждения, `confirmed` — подтверждён; факт клиента всегда подтверждён |
| `key` | о чём факт, например `markets.import_share`: факты с одним ключом конкурируют |
| `evidence` | на что опирается автоматический факт — признаки профиля или поля выгрузки; без основания автоматический факт не сохранится |
| `version`, `created_at` | номер и время версии |

Правка и удаление не перезаписывают факт, а добавляют новую версию: вся история остаётся в таблице `knowledge_facts`, и видно, что и когда исправил клиент. Действующая база знаний (`KnowledgeBase`) собирается из последних версий:

1. удалённые факты выпадают;
2. из фактов с одним ключом остаётся один: клиент главнее данных банка, данные банка главнее системы; при равенстве подтверждённый главнее предположения, затем новее;
3. уступившие факты лежат в `superseded` — там видно, какую догадку системы поправил клиент;
4. факты без ключа не конкурируют.

Если клиент удалит свой факт, снова действует автоматический. Если клиент подтвердит автоматический факт, тот становится фактом клиента. Номер сохраняемой версии проверяется: пропуск или повтор версии отклоняются.

### Черновик из данных банка

Задача A2-13: `draft` и `sync_draft` в `app/profile/knowledge.py`. Черновик собирается из профиля компании без веб-поиска, все факты — предположения (`assumption`) до подтверждения клиентом, и у каждого в `evidence` признаки профиля, из которых он собран.

| Ключ | Категория | Источник | Откуда |
| --- | --- | --- | --- |
| `products.industry` | `products` | `bank_data`, а если отрасль угадана по названию — `system` | `feature:industry` |
| `company.size` | `other` | `bank_data` | выручка, размер, численность |
| `bank.products` | `other` | `bank_data` | продукты в банке |
| `constraints.debt` | `constraints` | `system` | зависимость от заёмных средств |
| `markets.foreign_trade` | `markets` | `bank_data` | ВЭД и страны ФТС |
| `markets.trade_direction` | `markets` | `system` | вероятное направление ВЭД |
| `constraints.sanctions` | `constraints` | `system` | недружественные страны и страны с риском платежей |
| `markets.regions` | `markets` | `bank_data` | регион, город, география присутствия |
| `customers.main`, `suppliers.main` | `customers`, `suppliers` | `bank_data` | отрасли крупнейших покупателей и поставщиков с долей оборота |
| `company.group` | `other` | `bank_data` | группа и её отрасли |
| `counterparty.<id>.role` | `customers`, `suppliers` | `legend` | роль контрагента из демо-легенды: покупатель, поставщик или перевозчик |

Взятое из выгрузки как есть помечено `bank_data`, наши оценки поверх неё — `system`: в интерфейсе видно, где данные банка, а где догадка системы.

У фактов черновика постоянные id (`draft:<компания>:<ключ>`), поэтому `sync_draft` при каждом запросе приводит черновик к текущему профилю, а не плодит копии: новое добавляет, изменившееся записывает новой версией, пропавшее из данных удаляет. Факты, которые клиент подтвердил, исправил или удалил, не трогает: решение клиента главнее данных. `knowledge_for(connection, company_id)` собирает профиль, обновляет черновик и возвращает действующую базу знаний — это вход для API правок (A2-14) и для агента.

## Правки клиента

Задача A2-14, маршруты — `app/api/knowledge.py`, влияние на профиль — `apply_knowledge` в `app/profile/knowledge.py`.

| Запрос | Что делает |
| --- | --- |
| `GET /api/companies/{id}/knowledge` | действующая база знаний: черновик из данных банка (обновляется при запросе) и правки клиента |
| `GET /api/companies/{id}/knowledge/history?fact_id=` | все версии фактов: кто, что и когда менял |
| `POST /api/companies/{id}/knowledge/facts` | новый факт от клиента: сразу «подтверждено клиентом» |
| `PATCH /api/companies/{id}/knowledge/facts/{fact_id}` | исправление: новая версия, факт становится фактом клиента; `expected_version` защищает от двойной правки |
| `POST /api/companies/{id}/knowledge/facts/{fact_id}/confirm` | клиент подтвердил предположение |
| `DELETE /api/companies/{id}/knowledge/facts/{fact_id}` | удаление: история остаётся, черновик факт не вернёт |

Ошибки: 404 — компании или факта нет (в том числе факт другой компании), 409 — факт удалён или изменён с момента чтения, 422 — неверное тело запроса.

Правка сразу влияет на профиль, а через него на отбор и выводы: `GET /profile` собирается на каждый запрос без кеша и учитывает базу знаний.

- Каждый факт клиента становится признаком профиля (`kind=knowledge`, «Со слов клиента: …»). В `source_fields` у него `knowledge:<id факта>`, так что вывод можно проследить до правки клиента.
- Если клиент указал направление ВЭД (`markets.trade_direction` = `import`, `export` или `both`), валютная чувствительность пересчитывается по его словам. Например, «мы экспортёр» превращает слабый рубль из риска в возможность.

## Вопросы на уточнение

Задача A2-15, модуль `app/profile/gaps.py`, схема [schemas/knowledge_gaps.schema.json](schemas/knowledge_gaps.schema.json). Система знает, чего она не знает: в каталоге `SLOTS` — то, что важно для отбора и выводов, но не следует из выгрузки.

| Ключ | О чём | Когда спрашиваем |
| --- | --- | --- |
| `markets.sales_regions` | рынки сбыта: регионы и страны | всегда, высокий приоритет |
| `markets.export_share` | доля экспорта в выручке и импорта в закупках | только при ВЭД, со списком стран из ФТС |
| `seasonality.peak` | пик продаж и потребность в оборотных деньгах | всегда; высокий приоритет у сезонных сегментов (продукты, розница, стройка, АПК…) |
| `products.main` | что даёт основную выручку | всегда, с видом деятельности по ОКВЭД в вопросе |
| `customers.main`, `suppliers.main` | ключевые покупатели и поставщики | если платежи не дали черновика |
| `constraints.main` | что ограничивает бизнес | всегда |
| `plans.next_year` | планы на год | всегда; при зависимости от долга — с вопросом о финансировании |

Вопрос не задаётся, если по его ключу в базе знаний уже есть факт. Если факт — предположение черновика, он попадает в `to_confirm` («верно ли?»), а не в вопросы. У каждого вопроса есть `why` — что изменится в сводке после ответа — и `based_on`: признаки профиля, из-за которых вопрос задан именно так.

Формулировки собираются из профиля по шаблонам, без LLM: вопрос не может выдумать факт о компании, а дневной бюджет модели остаётся на интерпретацию новостей.

| Запрос | Что делает |
| --- | --- |
| `GET /api/companies/{id}/knowledge/questions` | вопросы по приоритету, предположения на подтверждение, сколько фактов уже подтвердил клиент |
| `POST /api/companies/{id}/knowledge/questions/{key}/answer` | ответ — `text` и `value` или `not_applicable: true` («не про нас») |

Ответ ложится в базу знаний фактом клиента с ключом вопроса. Если по ключу уже был факт черновика, ответ становится его новой версией, а не вторым конкурирующим фактом. После ответа вопрос пропадает, а ответ сразу виден в профиле как признак «Со слов клиента: …».

## Демо-легенда

Задача A2-10, решение — [ADR 0003](decisions/0003-demo-legenda.md), модуль `app/profile/legend.py`, файл `data/samples/legends.yaml` (путь задаёт `LEGEND_FILE` относительно `DATA_DIR`). Выгрузка обезличена, поэтому для демо у шести компаний (трёх из выгрузки кейса и трёх синтетических) и их крупнейших контрагентов есть вымышленные названия.

| Что задаёт легенда | Куда попадает |
| --- | --- |
| название, описание, бренды компании | `CompanyProfile.legend` |
| название контрагента или компании группы | `legend.name` у `counterparties`, `related_companies`, `group.members` |
| роль контрагента у клиента: покупатель, поставщик, перевозчик | `legend.role` у контрагента и факт базы знаний `counterparty.<id>.role` с источником `legend` |
| отрасль контрагента, которого нет в выгрузке юрлиц | `legend.industry` и `legend.segment`; если отрасль есть в выгрузке, поля пустые — правы данные |

Легенда — только слой отображения. `load_profile` собирает профиль по выгрузке и потом накладывает названия, признаки и чувствительность при этом не меняются, тест это проверяет. Условное название в поиск новостей не идёт: из легенды в поиск можно брать только `legend.segment` контрагента, которого нет в выгрузке. Роль из легенды — предположение с самым низким приоритетом: клиент подтверждает или исправляет её в вопросах на уточнение, и его ответ главнее.

Без файла, с пустым или битым файлом сервис работает на идентификаторах — битый файл пишет предупреждение в лог. Файл перечитывается при изменении, перезапуск не нужен.

## Связанные компании

Задача A2-16, модуль `app/profile/links.py`, маршруты — `app/api/links.py`, схема [schemas/linked_companies.schema.json](schemas/linked_companies.schema.json). Это главное, чем мы отличаемся: окружение клиента видно по платежам банка, а не только по его отрасли. Карточка связанной компании собирается из трёх источников данных банка и из того, что сказал клиент.

| Откуда связь (`origins`) | Что в карточке |
| --- | --- |
| `payments` | оборот по направлениям: `incoming` — компания платит клиенту, `outgoing` — клиент платит ей; сумма (`PAY_AMT`), число платежей (`PAY_CNT`) и доли среди **всех** платежей направления по сумме (`amount_share`) и по числу (`count_share`) |
| `group` | компания из той же группы (`GROUP_ID`); если она ещё и контрагент, это одна карточка с двумя источниками |
| `shared_person` | компания, с которой клиента связывает общее физлицо |
| `client` | компания, которой нет в данных банка: её добавил клиент |

В карточки попадают 30 крупнейших по обороту контрагентов и все контрагенты, у которых тип связи уже известен. К ним добавляются 20 крупнейших по выручке компаний группы, связанные через физлиц и добавленные клиентом. Сколько контрагентов не показано, видно в `hidden`. Итоги по всем платежам лежат в `incoming` и `outgoing` ответа.

Тип связи (`role`: `buyer`, `supplier`, `carrier`) задаёт клиент. Чья версия действует, видно в `role_source`:

1. `client` — тип назвал клиент. Для компании из данных банка его ответ хранится фактом базы знаний `counterparty.<id>.role`: в `role_fact_id` ссылка на него, а история правок — в `/knowledge/history`. Если у факта уже была версия из легенды, ответ клиента становится следующей версией этого факта.
2. `legend` — тип из демо-легенды.
3. `payments` — догадка по направлению платежей: только платит клиенту — вероятно покупатель, только получает от клиента — поставщик. Если платежи идут в обе стороны, тип не угадываем.

Перевозчика по платежам не отличить от поставщика, поэтому его отмечает клиент. Факт клиента сразу виден в профиле признаком «Со слов клиента: …». Если отмеченный перевозчик получает от 10% платежей направления (порог тот же, что у отраслей контрагентов в графе), у профиля появляется чувствительность к логистике: «Со слов клиента, перевозчики получают заметную долю ваших платежей: U_900102 — 40%. Рост тарифов и перебои в перевозках отразятся на сроках и затратах». Если такая чувствительность уже была (перевозчик из отрасли «Транспорт и логистика»), второй не появляется: к уже имеющейся добавляются ссылка на ответ клиента и пояснение. Мелкий перевозчик чувствительности не даёт, чтобы новости о тарифах не попадали к тем, у кого перевозки — малая доля оборота. Роль из легенды на чувствительность не влияет: легенда — только отображение (ADR 0003).

Компания, добавленная руками, хранится в таблице `manual_links`: название, тип связи, отрасль словами и (или) код ОКВЭД, комментарий. В профиле она становится признаком `feature:link:<id>` с `source_fields` = `links:<id>`. Если отрасль удалось распознать, появляется ещё и отраслевая чувствительность: «Ваш перевозчик ООО „Северный терминал“ работает в отрасли „Транспорт и логистика“: рост тарифов и перебои в перевозках отразятся на сроках и затратах». Значит, отбор найдёт новости рынка этой компании. При удалении запись только помечается удалённой.

| Запрос | Что делает |
| --- | --- |
| `GET /api/companies/{id}/links` | карточки связанных компаний и итоги платежей |
| `PUT /api/companies/{id}/links/{card_id}/role` | клиент задаёт тип связи, `{"role": "carrier"}`; ответ — обновлённая карточка |
| `POST /api/companies/{id}/links` | клиент добавляет компанию: `name`, `role`, по желанию `industry`, `okved_code`, `note` |
| `DELETE /api/companies/{id}/links/{card_id}` | удаление компании, добавленной клиентом; связи из данных банка не удаляются |

Ошибки: 404 — нет компании, карточки или добавленной компании с таким id; 422 — неверное тело запроса (пустое название, неизвестный тип); 503 — выгрузка не загружена.
## Конкуренты

Задача A2-17, модуль `app/profile/competitors.py`, маршруты — `app/api/competitors.py`, схема [schemas/competitors.schema.json](schemas/competitors.schema.json). Связь конкурента с клиентом всегда одна — «работают на одном рынке» (ADR 0003). Кандидаты приходят из трёх источников (`source`), и у каждого в `reasons` написано, почему он в списке.

| Источник | Как находим | Что даёт |
| --- | --- | --- |
| `bank_data` | компании выгрузки того же класса ОКВЭД (первые две цифры) с выручкой в пределах трёх раз от выручки клиента; компании группы и контрагенты по платежам не считаются, они есть в связанных компаниях | 10 самых похожих по сходству `score`: тот же код ОКВЭД — 0,5, та же группа — 0,4, тот же класс — 0,25; плюс до 0,3 за близость выручки и 0,2 за тот же регион |
| `open_source` | реальные игроки отрасли из Wikidata, только для демо-легенды (см. ниже) | названия идут в поиск новостей |
| `client` | компанию назвал клиент | названия идут в поиск новостей |

Компании из выгрузки обезличены, поэтому в поиск новостей не идут. Зато они показывают, с кем клиент делит рынок в базе банка. Без кода ОКВЭД или выручки подобрать их нельзя, и это проговаривается в `warnings`.

Конкуренты с настоящим названием (`open_source` и `client`) попадают в профиль. Это признак `feature:competitors` (`kind=competitor`) и чувствительность к теме `company`: в её ключевых словах названия без кавычек и организационно-правовой формы («ПАО „Акрон“» → «Акрон»). Так отбор находит новости о сделках, ценах и проблемах конкурентов.

Список правит клиент, решения хранятся в базе знаний под ключом `competitors.<id>`, история правок остаётся:

| Запрос | Что делает |
| --- | --- |
| `GET /api/companies/{id}/competitors` | список: сначала названные клиентом, потом из открытых источников, потом из базы банка по сходству; исключённые клиентом — в `excluded` |
| `POST /api/companies/{id}/competitors` | клиент называет конкурента, `{"name": "..."}`: факт со значением `true` |
| `DELETE /api/companies/{id}/competitors/{competitor_id}` | названного клиентом — удаляет, кандидата системы — исключает (факт со значением `false`) |
| `POST /api/companies/{id}/competitors/{competitor_id}/restore` | вернуть исключённого кандидата |

### Поиск по открытым источникам

Для демо-компаний реальных конкурентов ищем сами, без AI-сервисов: SPARQL-запрос к [Wikidata](https://query.wikidata.org/) (данные под лицензией CC0). Отбираются действующие российские компании (`P17 = Q159`, без `P576`) из отраслей (`P452`), сопоставленных сегменту ОКВЭД в `WIKIDATA_INDUSTRIES`, сначала самые известные (по числу статей в Википедии). Местные игроки помечаются по штаб-квартире (`P159`) и её региону (`P131`).

```
cd backend
uv run python scripts/find_competitors.py 46.75 --region Москва
```

Скрипт печатает блок `competitors` для `data/samples/legends.yaml`. Поиск шумный: в «транспорт и логистику» попадают исторические железные дороги, в «продукты питания» — банк. Поэтому в легенду кладём только тех, кто действительно работает на рынке клиента, со ссылкой на карточку Wikidata в `url`. Во время работы сервиса сеть для этого не нужна: список читается из легенды.

## Как используем в решении

- Профиль компании собираем из `df_Uid_data_hack.csv`: отрасль и её словесная формулировка, размер, стадия, продукты банка, внешнеэкономическая активность, регион.
- Контрагентов и зависимость от них берём из платежей: кто получатель, кто плательщик, какие объёмы и частота.
- Группу компаний — через `GROUP_ID`: событие про одного участника группы может касаться остальных.
- География — `CITY` и `REGION` у компании, `CITY_NAME` и `RC_NAME` у связанных лиц: региональные новости отбираем по ним.

## Аналитика банка

Организаторы дают материалы Центра макроэкономических исследований Альфа-Банка (обзоры инфляции, ставки ЦБ, рынков, макростатистики, тактический взгляд на квартал). Они лежат в той же ленте, что и новости, но помечены как позиция банка: в выводе ссылка на них отвечает за вопрос «как это оценивает банк».
