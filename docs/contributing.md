# Как вносим изменения

## Ветки

`main` защищён: прямые коммиты запрещены, изменения приходят через pull request с зелёными проверками. Перед слиянием должны проходить три проверки:

- `backend` — формат, линтер, типы, тесты, актуальность lock-файла;
- `frontend` — линтер, типы, сборка, актуальность lock-файла;
- `deployment` — Docker-сборка пяти сервисов, HTTP, PostgreSQL и очередь worker.

Предупреждения считаем ошибками: жёлтая сборка чинится до слияния, а не после сдачи.

Имя ветки: `<тип>/<область>-<суть>`. Если задача заведена в issue, добавляем её номер в конец: `feat/news-rss-collector-23`. В имени только латиница в нижнем регистре, цифры и дефисы.

Типы:

| Тип | Когда |
| --- | --- |
| `feat` | новая функциональность |
| `fix` | исправление поведения |
| `refactor` | переделка без изменения поведения |
| `test` | тесты и фикстуры |
| `docs` | документация |
| `ci` | сборка, рулсеты, окружение |
| `chore` | рутина: зависимости, конфиги |
| `spike` | разведка, результат которой — решение, а не код |

Области — по папке, в которой основная часть изменений, см. таблицу «Зоны кода» ниже. Для документации — `docs`, `adr-NNNN`, `readme`.

## Зоны кода

Папка определяет и зону роадмапа, и область в имени ветки. Если PR заметно задевает две зоны, его лучше разрезать: так проще откатить и понятнее история.

| Папка | Зона роадмапа | Область |
| --- | --- | --- |
| `backend/app/data`, `backend/scripts`, `data/` | Данные | `data` |
| `backend/app/profile` | Данные | `profile` |
| `backend/app/news` | Данные | `news` |
| `backend/app/rank` | Данные | `rank` |
| `backend/app/llm` | AI | `llm` |
| `backend/app/agent` | AI | `agent` |
| `backend/app/api` | Бэкенд | `api` |
| `backend/app/core`, `backend/app/main.py` | Бэкенд | `core` |
| `backend/app/worker` | Бэкенд | `worker` |
| `backend/app/contracts`, `docs/schemas` | Смежное | `arch` |
| `frontend/` | Фронтенд | `frontend` |
| `compose.yaml`, `deploy/`, `.dockerignore` | Смежное | `deploy` |
| `.github/`, `scripts/`, корневые конфиги | Смежное | `repo` или `ci` |
| `docs/` | Смежное | `docs`, `adr-NNNN`, `readme` |

Тесты идут в ту же область, что и код, который они проверяют: `test(profile): ...`.

## Связь с роадмапом

ID задачи из роадмапа (`A2-15`) пишем в описание PR, в строку «Задача роадмапа» шаблона. В имя ветки и в заголовок PR ID не пишем: заголовок становится коммитом в `main` и должен читаться как история изменений, а не как список номеров.

Когда PR слит, в таблице роадмапа ставим статус «ГОТОВО», а в комментарий задачи — номер PR. Так по таблице можно дойти до кода, а по коду — до задачи.

## Коммиты и PR

Формат заголовка: `<тип>(<область>): <что сделано>`. Тип и область берём из имени ветки, без сути и номера issue.

Текст после двоеточия — по-русски, с маленькой буквы, без точки в конце, желательно до 72 символов. Описываем результат, а не процесс: «добавил отбор новостей по ОКВЭД», а не «поправил ошибки». Названия библиотек, команд и полей данных остаются на английском: `feat(rank): добавил BM25-отбор по MAINOKVED_NAME`.

Все коммиты в ветке используют один и тот же префикс. Заголовок PR обобщает ветку целиком, а не повторяет последний коммит. Номер issue указываем в описании PR: `Closes #23`.

Тело PR заполняем по шаблону: что сделано, зачем (ID задачи из роадмапа и критерий кейса), как проверить, чек-лист.

## Слияние

Одна ветка — одна задача, ветка живёт недолго: создаётся от свежего `main` и удаляется сразу после слияния.

Вливаем только Squash and merge. Merge commit и rebase выключены на уровне репозитория и запрещены рулсетом. Заголовок PR становится единственным коммитом в `main`, поэтому перед слиянием его нужно перечитать и при необходимости поправить.

Ревью мы не делаем: PR нужен ради проверок и чистой истории, апрув рулсетом не требуется. Поэтому перед слиянием автор сам подтягивает свежий `main` в свою ветку и прогоняет проверки локально — красная сборка в `main` будет стоить дороже, чем две минуты на прогон.

## Что не попадает в репозиторий

- Секреты: ключи, пароли, токены. В репозитории живёт только `.env.example` с пустыми значениями, реальные значения — в локальном `.env` и в секретах стенда.
- Выгрузки кейса и любые производные от них файлы с данными. Подробности — в [data.md](data.md).
- Артефакты сборки, виртуальные окружения, кэши — они перечислены в `.gitignore`.

Новая прямая зависимость появляется в PR вместе с обновлённым lock-файлом и строкой в `THIRD_PARTY_NOTICES.md`.
