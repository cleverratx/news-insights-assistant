# Собственный оркестратор

A5-01, `backend/app/agent/orchestrator.py`. Это основа последовательного агента:
планировщик выбирает следующий шаг с учётом накопленных результатов, оркестратор
вызывает инструмент из реестра, сохраняет наблюдение и снова обращается к планировщику.
Готовых агентных фреймворков и новых зависимостей нет.

## Контракт выполнения

`Orchestrator(planner, registry, limits).run(profile, news, objective)` возвращает
`RunResult` с общим `AnalysisContext`: `run_id`, цель, профиль компании, материалы,
выполненные шаги и известная стоимость вызовов планировщика. Перед каждым решением
планировщик получает остаток шагов и времени.

Планировщик реализует `next_step(context, tools) -> Planning`. Решение `Decision` —
`tool` с именем инструмента и аргументами либо `finish` с результатом. `reason` —
короткая цель действия, а не скрытая цепочка рассуждений. После ошибки инструмента
планировщик видит её в следующем контексте и может выбрать другое действие.

Реестр `ToolRegistry.register(name, description, handler)` принимает асинхронный
обработчик `(context, arguments) -> Observation`. В наблюдении — JSON-данные и id
источников. Дубли имён запрещены. Неизвестный инструмент не исполняется: в контекст
попадает ошибка. Реестр фиксируется на начало каждого разбора.

Профиль, материалы, аргументы и результаты копируются. Планировщик и инструмент
получают снимок контекста; результаты добавляет оркестратор. Так изменение чужого
снимка не переписывает журнал и не смешивает параллельные разборы.

## Ограничения

`Limits` по умолчанию: 8 попыток планировщика, 60 секунд на весь разбор, 15 секунд
на один инструмент. Завершающее решение и исправление невалидного ответа тоже расходуют шаг. Ошибки и повторы
не обнуляют лимит. Время считается монотонными часами; общий таймаут охватывает
планирование, обращения к LLM с её внутренними ретраями и вызовы инструментов.

Статусы результата:

- `completed` — планировщик завершил анализ; результат в `output`;
- `step_limit` — достигнут предел решений, частичные наблюдения сохранены;
- `timeout` — исчерпано общее время, незавершённая операция отменяется;
- `planner_error` — планировщик недоступен или не вернул допустимое решение;
- `check_failed` — критик не подтвердил черновик; непроверенный текст не возвращается в output.

Ошибка и таймаут отдельного инструмента записываются в `Step`, после них можно
перепланировать. Внешняя `asyncio.CancelledError` передаётся вызывающему коду.
Таймауты кооперативные: обработчики должны использовать async I/O и уважать отмену;
блокирующий синхронный код не следует запускать внутри event loop.

## Подключение LLM

`LLMPlanner` использует существующий клиент A1-07, `Task.INTERPRET` и разрешённую
smart-модель. Дневной бюджет, резервирование расходов, тарифы и ретраи остаются
в `app/llm`. Планировщик получает реестр, профиль, материалы и предыдущие наблюдения.
Если полный контекст превышает лимит клиента, разбор прекращается с `planner_error`;
автоматической обрезки с потерей источников нет.

Стоимость корректного ответа и ответа с невалидным JSON учитывается в контексте.
При ошибке сети точная стоимость может быть неизвестна: учёт резерва в Redis остаётся
за LLM-клиентом; `cost_rub` разбора не является сверкой с балансом провайдера.
В логи пишутся run_id, номер шага, действие, инструмент, статус, длительность и известная
стоимость; тексты источников, сырые ответы модели и детали исключений не логируются.

Пример подключения в асинхронном сервисном коде (профиль и события загружены вызывающим):

```python
from app.agent.orchestrator import LLMPlanner, Orchestrator
from app.agent.critic import InsightCritic
from app.agent.tools.builtin import create_tools
from app.core.db import get_pool
from app.llm.client import open_llm_client

pool = await get_pool()
async with pool.acquire() as connection, open_llm_client() as llm:
    registry = create_tools(connection)
    result = await Orchestrator(LLMPlanner(llm), registry, critic=InsightCritic(llm)).run(
        profile, news, "Оценить влияние события на компанию"
    )
```

A5-01 не публикует новый HTTP endpoint и не выдаёт `output` за проверенный `Insight`.
JSON-протокол и коррекция невалидных вызовов реализованы в A5-02 (ниже). Конкретные инструменты реализованы в A5-03 (ниже); контекст между шагами реализован в A5-04 (ниже), критик — A5-05, сборка
инсайта по шести вопросам — A5-06, постоянное хранение трассировки — A5-08.


## Протокол инструментов (A5-02)

`app/agent/tools/__init__.py` содержит `Decision`, `Observation`, `ToolResponse`, `ToolError`
и реестр инструментов. Старые импорты типов через `orchestrator` сохранены.
JSON-схемы: [agent_decision.schema.json](schemas/agent_decision.schema.json),
[tool_response.schema.json](schemas/tool_response.schema.json).

Решение — один JSON-объект:

```json
{"action":"tool","reason":"Уточнить прогноз ставки","tool":"lookup","arguments":{"q":"ключевая ставка","limit":5}}
```

Или завершение:

```json
{"action":"finish","reason":"Данных достаточно","output":{"summary":"…"}}
```

Разбор строгий: лишние поля, пустая причина, противоречащие action поля, дубли ключей,
NaN/Infinity, JSON-массив вместо решения, Markdown и текст вокруг JSON отклоняются.
Схемы отражают зависимости полей от action/status, а не только их типы.

При регистрации передайте `arguments_model` и `result_model` — Pydantic-модели
с `extra="forbid"`. Их схемы передаются планировщику. Аргументы валидируются строго
до обработчика: строки не превращаются в числа, bool не заменяет int, дефолты модели
добавляются. Обработчик получает JSON-словарь. `result_model` проверяет `Observation.data`
после вызова. Некорректный результат не попадает в наблюдение.
Без моделей сохраняется совместимость A5-01: проверяется только общий JSON-конверт;
это не заменяет схему аргументов конкретного инструмента.

Ответ шага:

```json
{"status":"ok","observation":{"data":{"count":1},"source_ids":["news:1"]},"error":null,"error_detail":null}
```

У неуспешного ответа `observation=null`, а `error_detail` содержит код и безопасное
описание ошибки. Коды: `unknown_tool`, `invalid_arguments`, `invalid_result`,
`tool_error`, `tool_timeout`; при разборе решения — `invalid_decision`.
Ошибки валидации содержат пути полей и тип нарушения, без входных значений и текста
исключений. Реальные параметры остаются в самом контексте вызова; он не предназначен
для публичного лога без отдельной политики доступа и маскирования.

`LLMPlanner(max_repairs=1)` один раз просит исправить синтаксически неверное решение
или неизвестный инструмент. Разрешено настроить 0–2 исправления. В подсказку передаётся
безопасная ошибка; сырой ошибочный ответ не повторяется. Неверные аргументы дают
`invalid_arguments` в журнале шага: следующая итерация видит ошибку и может исправить
аргументы, поменять инструмент или завершить анализ. Каждый новый ответ расходует шаг.
Повторы сохраняют общий дедлайн и используют тот же клиент с дневным бюджетом.
Учитываются все уже оплаченные ответы, в том числе если исправление не удалось,
провайдер недоступен или общий дедлайн истёк во время повторного запроса.

JSON-протокол не вводит автоматическое выполнение кода и не добавляет конкретные
инструменты A5-03. Платные запросы для проверки реализации не требуются.


## Прикладные инструменты (A5-03)

`create_tools(connection)` из `app.agent.tools.builtin` регистрирует шесть инструментов.
Пакет `app/agent/tools/` заменил одноимённый модуль; старые импорты протокола сохранены.
Все инструменты имеют закрытые входные/выходные модели и работают в контексте текущего
клиента. Аргумента `company_id` нет: модель не может переключить профиль компании.

| Инструмент | Аргументы | Результат |
| --- | --- | --- |
| `get_profile` | пустой объект | Снимок CompanyProfile из контекста, с клиентскими правками и id признаков |
| `search_news` | `query`, `limit` 1–10 (5), `days` 1–14 (14), `markers` | SearchResult только по новостям, цитаты, ссылки и id фрагментов |
| `search_bank_analytics` | `query`, `limit` 1–10 (5) | SearchResult только по аналитике банка; старые PDF не отсекаются новостным окном |
| `get_counterparty_graph` | пустой объект | Актуальные карточки связей A2-16: роли, группа, платежи и доли; статус доступности |
| `calculate_exposure` | `direction=incoming|outgoing`, `partner_ids`, `segments` | Сумма и доля выбранных платежей относительно всех платежей направления |
| `get_original` | `doc_id`, необязательный `fragment_id`, `max_chars` 100–8000 (4000) | Дословная выдержка, источник, URL, дата, локатор и явный признак обрезки |

Поиск использует A3-07 (BM25 и готовый кеш переранжирования); вложенных новых вызовов
LLM нет. `source_ids` наблюдений содержат реальные id материалов или признаков профиля.
Перейти от результата поиска к оригиналу можно через пару `doc_id`/`fragment_id`.
Оригинал берётся из снимка события либо сохранённых таблиц `news_items` и
`analytics_documents`. Инструмент не скачивает URL, не читает произвольные файлы и не
запускает команды. Нет документа/фрагмента — `not_found`; нет хранилища — `unavailable`.
Текст не пересказывается: возвращается точная выдержка и `truncated=true`, если она обрезана.

Расчёт платежей вынесен в `app/profile/exposure.py`: использует все записи направления
через сервис графа, а не топ-5/топ-10 карточек. Суммы считаются Decimal.
`incoming` — клиент получает деньги от покупателей, `outgoing` — платит поставщикам.
Если заданы и partner_ids, и segments, фильтры применяются совместно (AND).
Без фильтров выбираются все платежи направления. Неизвестная отрасль не приписывается
контрагенту: её оборот показан отдельно; при отраслевом отборе есть предупреждение.
При нулевом обороте доля равна null, а не выдуманному проценту. Это доля платежей,
а не прогноз убытков, выручки или валютной позиции. Источник — PAYER/BENEFICIARY/PAY_AMT.

Если граф недоступен, ответ содержит `status=unavailable` и `graph=null` — нулевые
остатки вместо отсутствующих данных не создаются. Ошибки подключения и повреждённые
записи обрабатываются оркестратором как ошибки инструмента, без выдачи ложных данных.

Полные схемы результатов доступны в реестре и проверяют ответы на сервере. В LLM
отправляются входные схемы и список полей результата (`result_fields`), чтобы определения
CompanyProfile и графа не занимали весь входной лимит ещё до начала анализа. Это не
отключает проверку результата. Размер первого запроса с шестью инструментами проверен
тестом относительно стандартного лимита клиента.

Реестр и подключённое соединение создаются на один разбор. Для параллельных разборов
нужно получать отдельные соединения пула; не следует запускать конкурентные запросы
на одном соединении asyncpg. Переиспользование наблюдений между шагами реализовано в A5-04 (ниже).


## Единый контекст между шагами (A5-04)

`app/agent/context.py` содержит `AnalysisContext`, `Step` и `ContextObservation`.
Импорты `AnalysisContext` и `Step` из `orchestrator` совместимы с предыдущей версией.

В одном разборе сохраняются:

- неизменяемые для планирования снимки компании и исходных событий;
- `started_at` — единый момент времени для поискового окна;
- `observations` — успешные ответы инструментов, их параметры, источник и номер шага;
- `steps` — история действий, ошибок и ссылок на полученные наблюдения;
- `known_source_ids()` — id признаков, исходных событий и материалов из наблюдений.

Оркестратор записывает наблюдение только после проверки схемы ответа. Планировщик
и инструменты получают глубокие копии: изменение снимка не переписывает общую память.
При завершении `RunResult` содержит итог и тот же контекст со всеми основаниями;
следующим задачам критика и генерации инсайта не нужно искать их заново.
Это доступные основания для вывода, а не автоматическая проверка его утверждений:
сверка ссылок и критик относятся к A5-05/A5-06.

### Повторное использование

Для инструмента с `cacheable=True` повторный запрос возвращает сохранённое наблюдение
без повторного обращения к БД или обработчику. Ключ — имя инструмента и нормализованные
аргументы после добавления дефолтов и валидации A5-02. Порядок ключей объекта не важен,
порядок элементов списка сохраняется. Другие параметры — отдельный результат.

Все шесть инструментов A5-03 допускают переиспользование в пределах разбора. Для новых
инструментов флаг по умолчанию false: операции с побочными эффектами нельзя автоматически
считать повторяемыми. В `Step.reused_from` записывается id исходного наблюдения,
`observation_id` указывает на используемый результат. Повторное решение всё равно
расходует шаг и подчиняется общему дедлайну; бесконечный цикл не получает бесплатных шагов.

Ошибки валидации, сбои и таймауты не попадают в кеш. Ответы со статусом `not_found`,
`unavailable` и пустые поисковые выдачи тоже не переиспользуются: следующая попытка может
найти данные. Они остаются в истории наблюдений, чтобы агент видел, чего не хватало.
Нулевой оборот с явно неопределённой долей — корректный расчёт, а не подмена отсутствия БД.

### Представление для модели

`planner_data()` передаёт каждый результат один раз в `observations`. Шаги содержат
`observation_id`, а не повторяют весь текст при каждом использовании. Получение профиля
ссылается через `context_ref=profile` на уже переданный полный профиль, если результат
действительно совпадает с ним. Исходные данные и источники не пересказываются моделью
для сжатия. Полная история с ответами остаётся в объекте контекста для проверки.
Лимит размера клиента A1-07 сохраняется: большие уникальные результаты не обрезаются молча.

Память изолирована по разбору и не хранится глобально в реестре или оркестраторе.
Новый запуск, другая компания или изменившийся профиль не получают старый кеш. Контекст
поддерживает JSON-сериализацию вместе с памятью; автоматического возобновления, хранения
в БД или переноса результатов между HTTP-запросами A5-04 не добавляет. Постоянная
трассировка — A5-08. Для согласованного снимка самой БД транзакцию задаёт вызывающий сервис;
контекст фиксирует профиль, события и результаты чтения, но не блокирует обновления БД.


## Критик и уточнение плана (A5-05)

`InsightCritic` из `app/agent/critic.py` подключается явно:
`Orchestrator(planner, registry, critic=InsightCritic(llm))`.
Без аргумента critic сохраняется общий режим A5-01 с произвольным JSON-результатом.
При включении критика планировщик получает схему черновика в `output_schema`, поэтому
знает структуру, которую нужно вернуть в `finish.output`.

Черновик содержит company_id, news_ids, шесть блоков (`what_happened`, `why_it_matters`,
`risks`/`opportunities`, `actions`, `bank_view`, `sources`). Утверждения используют
локальные source_ids, а SourceRef ссылается на реальный материал или признак профиля.
Принимаются метаданные полного Insight, но его self_check не служит доказательством;
неизвестные поля вне контракта не допускаются. Генерация полного Insight — A5-06.

Сначала работают детерминированные проверки:

- компания и основное событие соответствуют общему контексту;
- заполнены событие, важность, последствия и действия;
- позиция банка описана, когда она найдена; если аналитика не найдена после реального
  поиска, её отсутствие допустимо, без придуманной позиции;
- id утверждений и источников уникальны, все ссылки разрешаются;
- каждый источник действительно получен в исходных материалах или инструментами поиска/
  получения оригинала; тип источника и URL совпадают;
- указанный фрагмент существует, цитата дословно присутствует в доступном тексте;
- важность опирается на признак компании, позиция банка отделена от вывода модели.

`known_source_ids()` сам по себе недостаточен: критик сверяет доступное содержание
материалов и фрагментов. Неполный get_original не доказывает существование произвольного
fragment_id: нужно запросить конкретный фрагмент либо сослаться на документ целиком.
Если структурная проверка не пройдена, лишнего LLM-вызова нет.

После неё smart-модель через клиент A1-07 проверяет смысл: поддерживаются ли утверждения
источниками, нет ли противоречий между ними, не подменён ли прогноз фактом, персональны
ли последствия и конкретны ли действия. Ей передаются черновик, профиль и реальные
выдержки источников (до 3000 символов на ссылку, без додумывания остального документа).
Смысловая проверка вероятностная: положительный ответ модели не является гарантией
безошибочности. Публичные цены по-прежнему оценочные.

Модель критика возвращает только список замечаний по известным id утверждений. Она не
может пометить собственные замечания resolved=true или отменить ошибки правил.
Невалидный ответ, неизвестный id, недоступная модель или исчерпанный бюджет не считаются
успешной проверкой. Уже известная стоимость ответа, включая невалидный, учитывается в
расходах разбора. Стоимость неизвестного сетевого исхода остаётся на учёте клиента A1-07.

Отклонённый черновик и отчёт попадают в `context.critic_reviews`, видимые следующему
планированию. Агент может уточнить запрос, получить оригинал или исправить утверждение,
а затем снова предложить finish. Критик сам инструменты не запускает и реестр не меняет.
Для новых данных нужен другой запрос/фрагмент: успешные прежние ответы по тем же аргументам
по-прежнему переиспользуются согласно A5-04.

`Limits.max_critic_reviews=2` (1–3) ограничивает проверки. Общие шаги и время не
обнуляются; внешний cancel сохраняется. При исчерпании попыток — check_failed,
при общем дедлайне — timeout, при исчерпании шагов — step_limit. В этих случаях
output=null, а черновики и замечания доступны в контексте. При успехе self_check в
ответе выставляет оркестратор с реальным числом проверок, а не модель.

Схемы: [insight_draft.schema.json](schemas/insight_draft.schema.json),
[critic_report.schema.json](schemas/critic_report.schema.json).
Тесты проверяют правила, протокол LLM, получение недостающего оригинала между проверками,
ограничение повторов и отказ от выдачи неподтверждённого результата. Смысловые ответы
в тестах подменены; качество критика на живой модели этим прогоном не измеряется.

## A5-06 и A5-07: проверенный персональный инсайт

`POST /api/companies/{company_id}/insights` принимает 1–3 различных `news_ids`
и необязательный `focus` (до 600 символов):

```json
{"news_ids":["news:example"],"focus":"Влияние на стоимость перевозок"}
```

Сервис загружает профиль и оригинальные материалы, запускает планировщик с шестью
вопросами и критика. `insight` содержит событие, важность для компании, риски и
возможности, действия, позицию банка и источники. Идентификаторы, время, оценка
релевантности и результат проверки назначаются сервером. Все выбранные материалы
должны присутствовать в проверенном ответе. Позиция банка допускается только в
`bank_view`; отсутствие найденной позиции явно объясняется.

`presentation` готовит данные для интерфейса: шесть `blocks`, отдельные `facts`,
`bank_position`, `ai_conclusions`, `client_context` с русскими метками происхождения.
Каждое утверждение содержит ссылки на источники. `originals` хранит исходные цитаты
и ссылки отдельно от текста ИИ. Экран инсайта относится к A6-04; этот API его не создаёт.
Схема ответа: [generated_insight.schema.json](schemas/generated_insight.schema.json).

В модель передаются ограниченные выдержки, явно помеченные как сокращённые;
сервер сохраняет полные материалы для проверки и `get_original`. При недоступной
LLM, ошибке или непройденной проверке возвращается `insufficient_data` с причиной
и исходными ссылками, без неподтверждённых утверждений. `usage` показывает фактически
полученные ответы, токены, модели и известную стоимость; `public_estimate` остаётся
оценкой по публичным тарифам. Реальные списания шлюза этим полем не подтверждаются.

Генерация может расходовать бюджет LLM. Ответ сохраняется вместе с трассой (A5-08). Готовый разбор тех же материалов для того же профиля, роли и акцента выдаётся из кеша без вызова модели (`cache_hit=true`, A5-09, см. [llm.md](llm.md#управление-стоимостью-a5-09)).
Автоматические тесты используют подмену LLM;
качество интерпретации на живых моделях ими не измеряется.


## A5-08: журнал разбора и сохранение результата

`POST /api/companies/{company_id}/insights` сохраняет результат и трассу в PostgreSQL.
Полученный `insight.id` используется для чтения:

- `GET /api/insights/{insight_id}` — сохранённый ответ генерации, включая представление и стоимость;
- `GET /api/insights/{insight_id}/trace` — журнал происхождения вывода.

Чтение не запускает LLM. Неизвестный ID возвращает 404, недоступное хранилище или
повреждённый сохранённый контракт — 503. При ошибке записи POST не сообщает об успехе.
Результаты `insufficient_data` тоже сохраняются: причина неудачи доступна в журнале.

`app/agent/trace.py` собирает трассу из серверного контекста:

- `steps`: решения планировщика (включая `finish`), короткая цель, параметры инструмента,
  статус выполнения, время планирования и инструмента, ссылки на наблюдение и проверку;
- `observations`: проверенные по схеме результаты инструментов. Повторный вызов ссылается
  через `reused_from` на ранее полученное наблюдение;
- `checks`: отчёты критика; `steps[].check_index` — индекс в этом массиве;
- `documents`: снимки исходных материалов и фактически полученных поисковых цитат/оригиналов;
- `profile_features`: признаки профиля на момент анализа, включая поля происхождения;
- `used_sources`: основания итогового инсайта. `ref_id` связывает источник с документом
  или признаком, `fragment_id` — с фрагментом, `statement.source_ids` — с утверждением;
- `usage`, `execution_status`, время начала/конца и общая длительность разбора.

Все просмотренные материалы сохраняются отдельно от списка оснований результата:
попадание документа в поиск само по себе не означает, что он использован в выводе.
План фиксируется как последовательность выбранных действий, без скрытых рассуждений,
сырых LLM-запросов, ключей доступа и отклонённых черновиков. Сообщения об ошибках
провайдера и БД заменяются служебными сообщениями.

Таблица `agent_insights` создаётся при первой генерации до вызова LLM. Результат и
трасса записываются одним INSERT в одну строку; `insight_id` и `run_id` уникальны,
обновления старого разбора нет. Снимки не перечитываются из текущего профиля или
новостной базы. Отмена незавершённого запроса не создаёт готовый инсайт.

Схема: [agent_trace.schema.json](schemas/agent_trace.schema.json). Отдельный UI панели
оснований — A6-05. Трасса содержит бизнес-данные и наследует текущий доступ API;
разграничение прав и маскирование чувствительных полей выделены в A7-03.


## Связь инсайта с оценками ленты

GET ленты сохраняет серверный снимок `feed_snapshots` и возвращает `snapshot_id`.
При открытии карточки POST принимает `feed_snapshot_id` и `role` (ceo/cfo/logistics).
Оценки из тела запроса не принимаются. API сверяет компанию, роль и хеши профиля и
материалов; при устаревшем снимке возвращает 409 до вызова LLM. После обновления
ленты запрос можно повторить. Без снимка используются общая функция важности,
заданная роль и явно обозначенная оценка влияния по правилам.

`GeneratedInsight.ranking` и `AgentTrace.ranking` сохраняют важность, влияние и
скоринг карточек под выбранную роль. Агент получает нейтральные оценки без должности (A5-14);
повторная платная оценка влияния не запускается. Внешние сведения по-прежнему проверяет критик.
Описание региональных правил и UI: [module-integration-review.md](module-integration-review.md).

### Лимиты живого прогона

Агентный протокол со схемами, профилем и оценками требует больше прежних 24 КБ входа.
По умолчанию клиент теперь допускает 128 000 байт и ответ до 8192 токенов;
`.env.example` содержит те же значения. Это верхние ограничения, а не обещанный
размер ответа или фактическая стоимость. Учёт бюджета и лимит входа сохраняются.
Генерация инсайта по умолчанию использует общий дедлайн 180 секунд (включая инструменты
и критика); явно переданный `Limits` имеет приоритет. Базовый Orchestrator остаётся
с прежними лимитами для остальных вызовов.

## A5-11: нехватка данных — честный ответ вместо догадок

Модуль `app/agent/fallback.py`. Критерий 4 кейса — минимум фактологических ошибок. Поэтому сервис не заполняет пробелы догадками: он называет, чего не хватило, и показывает только проверенное.

### Цифры только из источников

Критик (`critic.checks`) извлекает из каждого утверждения черновика числа и ищет их среди:
- текстов, абзацев и ключевых фактов материалов разбора;
- найденных цитат и оригиналов;
- заголовков и дат материалов;
- профиля компании, включая признаки и код ОКВЭД.

Правила сравнения:
- `14,0%` равно `14%`;
- допустим перевод масштаба: `3,3 млрд` = `3 300 млн`, выручка `2e10` = `20 млрд`;
- допустимо округление до точности, с которой число записано в выводе.

Небольшие счётные числа без единиц («3 шага», «2 квартала») не проверяются. Число с единицей (`%`, `п.п.`, `₽`, `млн`…) проверяется всегда. Цифра, которой нет ни в одном источнике, — замечание `Цифра без источника`, и агент получает его как ошибку для исправления.

**Спасение проверенного остатка.** Если после всех попыток критик отклоняет черновик только из-за таких цифр, утверждения с ними убираются. Остаток проходит полную проверку ещё раз, включая смысловую. Если она пройдена, инсайт готов, а в `gaps` отмечено, сколько выводов скрыто. Если есть другие проблемы (выдуманная цитата, чужая компания), ничего не спасается.

### Чего не хватило: `GeneratedInsight.gaps`

Каждый пробел — `DataGap`:
- `kind` — вид пробела;
- `missing` — чего не хватает;
- `consequence` — что из-за этого;
- `remedy` — как восполнить;
- `blocking` — из-за пробела вывод не сформирован;
- `details` — замечания проверки;
- `question_keys` — вопросы базы знаний компании;
- `news_ids` — материалы.

| `kind` | Когда | Блокирующий |
| --- | --- | --- |
| `model` | модель недоступна, план некорректен, таймаут, не хватило шагов | да |
| `verification` | вывод не прошёл проверку критика | да |
| `numbers` | скрыты выводы с цифрами без источника; или готовый вывод без единой цифры в рисках и возможностях — оценка только качественная | нет |
| `bank_view` | готовый вывод без позиции банка: выводы ИИ не являются позицией банка | нет |
| `source_text` | от материала доступен только анонс (меньше 600 знаков) | нет |
| `company_data` | по теме новости в профиле нет ответа на вопрос базы знаний (доля экспорта при новости о курсе, поставщики при новости о сырье…), до двух вопросов | нет |

У готового инсайта не бывает блокирующих пробелов: это проверяет контракт. Вопросы берутся из каталога `app/profile/gaps.py` и не задаются, если клиент уже ответил (в профиле есть признак `feature:knowledge:<ключ>`).

### Без персонального вывода — только проверенные факты

Если вывод не готов (модель недоступна или проверка не пройдена), `what_happened` заполняется ключевыми фактами новости со статусом `confirmed` или `reported`, не больше трёх. Это факты, которые уже прошли сверку с абзацем при извлечении (A3-04). У `reported` указано, чьи это слова. Источник каждого факта — ссылка на абзац. Причин, рисков, действий и позиции банка в таком ответе нет.

### Проверка

`tests/test_agent_fallback.py`:
- сравнение цифр с источниками и масштабами;
- замечание критика до вызова модели;
- спасение остатка с повторной проверкой и записью в трассу;
- отказ спасать при других проблемах;
- факты без модели;
- пробелы готового вывода, вопросы по темам, короткий материал;
- запрет блокирующего пробела у готового инсайта.

Живой прогон 22.10.2026 на синтетических материалах из тестов (DeepSeek в роли сильной модели):
- профиль почти без значений, материал в 78 знаков — сервис отказался от вывода с блокирующим пробелом `verification`, подробностями критика и пробелом `source_text`;
- прогон выявил ложное срабатывание на коде ОКВЭД из профиля, исправлено: в пул цифр входит весь профиль.

При живом запуске учтите: агенту нужен `LLM_MAX_INPUT_BYTES=128000`, со старым значением 24000 планировщик не стартует. GLM в роли сильной модели на этом прогоне не уложился в общий дедлайн 180 секунд.

## A5-12: продукт банка — только когда он обоснован

Модуль `app/agent/offers.py`. Кейс допускает нативную рекламу продуктов банка, а эксперты просят рекомендовать по контексту компании и инсайта, без агрессивных кросс-продаж. Поэтому предложение строится правилами, а не моделью, и показывается редко.

### Правила

| Продукт | Тема события | Основание в профиле компании |
| --- | --- | --- |
| `loan` — пересмотр условий долга | ключевая ставка, долговой рынок | `debt_dependence`, `loan`, `finance_payments` |
| `deposit` — свободная ликвидность | ставка, инфляция | `deposit` |
| `guarantee` — вместо предоплаты по ВЭД | торговля, санкции, регулирование | `customs` |
| `settlement` — расчёты по ВЭД | курс, санкции, торговля | `payment_hub_trade`, `unfriendly_trade` |
| `factoring` — деньги за отгрузку сразу | потребление, отрасль, компания, ставка | `customer_concentration`, `factoring` |
| `leasing` — транспорт и техника | логистика, сырьё, ставка | `leasing` или сегмент: логистика, стройка, агро, авто |

Предложение (`GeneratedInsight.offer`) появляется, только если выполнены все условия:

1. инсайт готов (`ready`) и значимость события не низкая;
2. тема материала совпадает с темой продукта, а у компании есть признак-основание;
3. есть риск или возможность инсайта, которые продукт закрывает, и связь подтверждена: вывод ссылается на признак-основание или в профиле есть чувствительность компании к этой теме через тот же признак.

Предлагается не больше одного продукта. Если подходят несколько, выбирается тот, что сильнее связан с выводами; продукт, который предложила сама модель, получает приоритет.

### Что видит пользователь

`ProductOffer` содержит:
- метку «Предложение Альфа-Банка»: отдельный блок, а не вывод ИИ;
- `why` — какое событие и какие признаки компании делают продукт уместным;
- `benefit` — что продукт даёт в этой ситуации;
- `statement_ids` — к каким рискам и возможностям он относится;
- `feature_ids` — основания;
- `next_actions` — по умолчанию «связаться с менеджером» и «заказать звонок»;
- `disclaimer` — «Не является инвестиционной рекомендацией…».

Если продукт уже подключён (`already_client`), речь о пересмотре условий, и заявки на новый продукт среди действий нет.

Контракт не допускает предложение в неготовом инсайте и предложение, не связанное с рисками или возможностями.

### Модель и критик

В цель агента добавляется список уместных продуктов с основаниями или прямой запрет: «продукты банка не предлагай». Критик отклоняет до смыслового вызова модели:
- действие `bank_product` с продуктом не из списка уместных;
- больше одного продукта в действиях.

### Проверка

`tests/test_agent_offers.py`:
- выбор продуктов по теме и признакам;
- подсказка модели;
- отклонение необоснованного продукта критиком;
- одно предложение в готовом инсайте с пересмотром условий для действующего клиента;
- отсутствие предложения без основания, при низкой значимости и без модели;
- ограничения контракта.

## A5-13: привязка каждого утверждения к фрагменту

Каждое утверждение инсайта хранит, из чего оно получено. Подтверждение ставит сервер (`app/agent/trace.py`, функция `ground`), а не модель.

### Поля утверждения

- `basis` — список оснований. Для документа: `source_id`, тип, `ref_id` материала, `fragment_id` абзаца или ключевого факта и дословная выдержка `quote`. Для признака компании: id признака и его формулировка.
- `support`:
  - `source` — подтверждено фрагментом документа;
  - `company_data` — подтверждено данными компании;
  - `assumption` — подтверждающего фрагмента нет: это **предположение модели**.

Как ставится:

| Происхождение | `source` | `company_data` | иначе |
| --- | --- | --- | --- |
| `fact` | есть фрагмент новости или аналитики | — | `assumption` |
| `bank` | есть фрагмент аналитики банка | — | `assumption` |
| `client_data` | — | есть признак компании | `assumption` |
| `model` | есть фрагмент документа | есть только признак | `assumption` |

Фрагмент находится по `fragment_id` источника или по его цитате: абзац с этой цитатой предпочтительнее всего текста. Ссылка на документ целиком, без абзаца и цитаты, фрагментом не считается.

### Что видит пользователь и что проверяется

- `presentation` показывает утверждение без подтверждения с меткой «Предположение модели» вместо «Вывод ИИ» или «Факт по источнику».
- Факт и позиция банка без `fragment_id` или цитаты не проходят критика: агент получает замечание и указывает абзац.
- Поля `basis` и `support` из ответа модели отбрасываются при разборе черновика и не показываются ей в схеме ответа: модель не может сама объявить вывод подтверждённым.
- Проверенные факты без модели (A5-11) ссылаются на абзац ключевого факта и получают `source`.

### Журнал

`AgentTrace.claims` — для каждого утверждения раздел, происхождение, `support` и основания. Контракт журнала проверяет, что:
- каждое основание совпадает с источником вывода;
- фрагмент есть в снимке документов, а выдержка дословно в нём содержится;
- `source` опирается на документ, а `company_data` — на признак.

При сохранении `claims` сверяются с утверждениями результата.

### Проверка

`tests/test_agent_grounding.py`:
- все утверждения готового инсайта привязаны к абзацам, выдержки есть в снимке, результат и журнал сохраняются и читаются;
- вывод, опирающийся на документ целиком, показан как предположение, даже если модель прислала «подтверждение»;
- факт без абзаца отклоняется критиком;
- модель не может передать `basis` и `support`;
- проверенные факты без модели сохраняют ссылки на абзацы;
- журнал не принимает выдуманную выдержку и подтверждение без основания.

## A5-14: инсайт под должность

Модуль `app/agent/roles.py`. Принцип: фактура общая, подача своя.

- **Разбор не зависит от должности.** Агент получает цель без роли и нейтральные оценки ранжирования. Факты, позиция банка, источники, выводы и их привязка к фрагментам одинаковы для CEO, CFO и руководителя логистики.
- **Роль меняет подачу** — поле `GeneratedInsight.role_view`:
  - `focus` — что важно должности;
  - `risks`, `opportunities`, `actions` — порядок утверждений;
  - `emphasis` — что роль увидит первым;
  - `headline` и `summary` — «главное для вас» со ссылками `summary_ids`;
  - `rewrites` — формулировки выводов модели языком этой должности.
- **Оценки карточек** (`ranking`) по-прежнему взвешиваются под должность (A4-11).

### Как строится подача

1. **Правила.** У каждой роли есть словарь акцентов и предпочтительные виды действий:
   - CFO — ставка, долг, курс, налоги, ликвидность, маржа; вопросы и продукт банка;
   - логистика — перевозки, поставки, тарифы, сроки, таможня;
   - CEO — рынок, спрос, выручка, конкуренты; сценарии.
   
   По ним сортируются риски, возможности и действия. Это `method=rules`, без модели.
2. **Модель.** Одним вызовом быстрой модели (`Task.SUMMARIZE`) переписываются только утверждения с происхождением `model`. Факты и позиция банка во вход не попадают. Ответ проверяется:
   - переписывать можно только выводы модели;
   - в новой формулировке нет цифр, которых не было в исходной;
   - `summary` опирается на указанные утверждения, и его цифры есть в них;
   - текст не длиннее двух исходных плюс 200 знаков.
   
   Нарушение отбрасывает конкретную формулировку. Если ничего не осталось, подача остаётся по правилам. Ответ кешируется (`llm_cache`, вид `role_view`).
3. **Любой сбой** — недоступность, лимит, некорректный JSON — даёт подачу по правилам, готовый инсайт не страдает.

Контракт не допускает:
- подачу роли для неготового инсайта или чужой должности;
- переписанные факты и позицию банка;
- порядок, который не является перестановкой утверждений раздела;
- ссылки на несуществующие утверждения.

### Смена должности без нового разбора

Ключ кеша инсайтов (A5-09) больше не включает роль. Повторный `POST /api/companies/{id}/insights` с теми же материалами и другой `role` берёт общий разбор из кеша (`cache_hit=true`, тот же `insight.id`). Для новой роли пересчитываются только оценки карточек и `role_view`. Агентный разбор не запускается, новая запись не создаётся.
