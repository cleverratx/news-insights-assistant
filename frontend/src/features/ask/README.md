# Уточняющий вопрос по инсайту

A6-06, критерий 10. Диалог находится внизу открытого разбора. Кнопка «Задать вопрос» под заголовком переводит фокус в поле ввода. Используются существующие компоненты Альфа-Бизнеса, токены и CSS Modules; новых зависимостей нет.

## Посмотреть

1. Запустить приложение по [инструкции разработки](../../../../docs/development.md), войти тестовым пользователем и открыть `/feed`.
2. Выбрать новость и дождаться разбора. Нажать «Задать вопрос».
3. Выбрать пример вопроса или написать свой. Примеры заполняют поле, отправка выполняется только пользователем.
4. Отправить кнопкой или Enter; Shift + Enter добавляет строку. В ответе доступны метки происхождения и раскрываемые источники. Ссылка в тексте раскрывает нужный источник именно этого ответа.

Для настоящих ответов нужны доступные API, PostgreSQL с материалами и настроенная LLM. Запросы могут расходовать бюджет модели. Сам frontend запускается отдельно, но ответы агента локально не выдумываются.

## API и контекст

Используется существующий `POST /api/companies/{company_id}/insights`, поле `focus`. Компания, все `news_ids`, должность, `feed_snapshot_id` и связанная компания берутся из открытого `GeneratedInsight`, а не из изменившейся ленты. Ответ с другими идентификаторами, ролью или снимком не попадает в диалог.

Лимит `focus` в действующем API — 600 символов. Полный текущий вопрос сохраняется; в оставшееся место добавляется явно сокращённый исходный вывод либо последний успешный вопрос и краткий ответ. Неуспешные и отменённые запросы не становятся контекстом следующего вопроса. Это уточнение существующего агентного разбора; отдельного серверного chat-endpoint и переноса внутренних наблюдений A5-04 между HTTP-запросами API не предоставляет.

История живёт в памяти открытого разбора. При закрытии, открытии другого инсайта, смене компании или должности она сбрасывается; незавершённый fetch отменяется. История не записывается в браузерное хранилище.

Во время запроса повторная отправка заблокирована, следующий вопрос можно подготовить в поле. «Остановить ожидание» отменяет клиентский fetch; уже израсходованный бюджет не возвращается. Ошибка сохраняет вопрос, повтор использует тот же `focus` без дублирования сообщения. При 409 предлагается обновить ленту и открыть разбор заново, снимок не снимается автоматически. Ответ `insufficient_data` показывает объяснение и доступные основания.

## Проверка

```bash
cd frontend
npm test
npm run lint -- --max-warnings=0
npm run typecheck
npm run build
```

`tests/ask.test.mjs` использует Node Test Runner и загрузку TypeScript через существующий Vite, не поднимает HTTP-сервер и не обращается к LLM. Проверяет сохранение контекста, отсутствие подмены настроек, продолжение разговора, лимит Unicode и отказ от ответа другого контекста. Запуск включён в проверку `frontend` в CI.

Браузерный сценарий: два последовательных вопроса, раскрытие источников без повторяющихся DOM-id, недоступность сервиса и повтор, нехватка данных, отмена и запоздалый ответ, смена события/должности во время ожидания, ввод 600 символов и проверка на мобильной ширине. API в таком прогоне следует подменять, чтобы не расходовать бюджет.
